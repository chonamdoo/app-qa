# QAutra 제품 재설계 기준 · Open Design 전달 문서

문서 기준일: 2026-11-01. 대상: Open Design, 제품 설계자, QA 담당자, 구현·검증 담당자.

**최종 권고: 시나리오·실행·결과 중심의 QA 앱을 만든다. AI의 병렬 실행 판단은 폐지한다. 확정한 시나리오를 제품 실행 엔진이 수행하고, 실행 Space는 그 과정을 보여 준다. VM은 필요할 때 사용하는 내부 실행 자원이지 사용자가 매 테스트마다 관리하는 단위가 아니다.**

이 문서는 제품 재설계의 전달 기준이다. 실제 기능 구현·배포 완료 또는 모든 제안에 대한 사용자 승인 기록은 아니다. 제품 수정·빌드·앱·브라우저·VM 실행은 계속 홀딩한다. 기존 실행 기록과 작업 중 변경은 보존한다.

## 1. 결정의 권위와 변경점

### 사용자가 명시한 결정

- AI가 QA의 병렬/순차 여부를 판단하고 자율 실행을 배치하는 기능은 폐지한다.
- 개발자·에이전트 전문가뿐 아니라 일반 QA 담당자가 시나리오를 제공하고 실행·결과·실패 영상을 사용할 수 있어야 한다.
- 반복 실행의 안정성·신뢰성·재현성을 제품 기준으로 다룬다.
- 특정 Excel 양식·열 이름·빌드 스크립트를 요구하지 않는다. 직접 전달한 자료와 앱 입력 모두 수용한다.
- VM 중심과 Ego형 Space, 테스트별 브라우저·모바일 기기 할당의 장단점·영향을 비교하고 설계 문서로 남긴다.

### 이 문서의 권고 결정

- **기본 실행은 순차.** 동시 실행을 제품에서 영구 제거하는 것이 아니다. 관리자가 검증한 환경·데이터 격리 계약과 고정된 엔진 규칙으로만 제한된 동시 실행을 허용한다. AI의 추천값이나 추론은 승인·자원 독립성의 근거가 아니다.
- AI는 문서 해석·작성·실패 원인 후보를 돕는 선택 기능이다. 확정된 회귀 시나리오 실행에는 모델 연결을 필수로 하지 않는다. 실행 중 AI의 경로 변경·기대값 변경·자동 수리 반영은 금지한다.
- 기본 제품은 Mac 설치형·로컬 작업 공간이다. 원격 worker는 명시적 연결·인증·데이터 정책이 있는 경우만 사용한다. 새 SaaS·조직 계정·CI·유료 기기 팜을 기본 요건으로 추가하지 않는다.
- 제품 UI는 시나리오/실행 관리 + Space형 관측을 채택한다. 일반 사용자에게 VM 생성·OS 설치를 테스트 시작 절차로 노출하지 않는다. 환경 준비 담당자를 위한 별도 관리 흐름을 제공한다.
- 실제 Chrome/Safari·모바일 웹·native·WebView는 대상별 지원 능력과 한계를 표시한다. 미지원 항목을 다른 엔진으로 실행하고 같은 대상의 PASS로 표시하지 않는다.

이 권고는 기존 에픽의 실제 대상·권한·증거·원본 보존·사용자 입력 비간섭 요구를 유지한다. 예전 문서의 “AI가 병렬 분할을 제안” 부분은 최신 사용자 결정으로 대체된다. 기본 순차는 과거 D05의 다중 모바일 요구를 삭제하거나 전체 상한을 영구 1로 고정한다는 뜻이 아니다.

현재 소스에서 별도 AI scheduler가 이미 구현돼 있다는 뜻은 아니다. 현행 queue도 코드로 기기/context 충돌을 처리한다. 폐지 대상은 **AI가 다음 실행 묶음·병렬 분할을 자율 결정하는 제품 역할**이며, 새 기본 순차 규칙은 기존 runner의 플랫폼 병렬 실행과 direct script의 다중 session 호출에도 적용해야 한다.

## 2. 제품이 약속하는 것과 약속하지 않는 것

### 약속해야 하는 것

1. 승인된 시나리오 revision의 단계·기대값·조건을 실행 중 바꾸지 않는다.
2. 실행 대상과 초기 상태를 확인하고 결과가 불명확하면 불명확하다고 알린다.
3. 원 TC·근거·실행 코드·환경·실행 시도·검증 결과·영상이 이어진다.
4. 실패·취소·연결 단절 뒤에도 기존 증거와 실제 효과를 보존한다.
5. 반복 실행할 때 바뀐 조건을 드러내고, 과거 PASS를 현재 버전의 PASS로 재사용하지 않는다.
6. QA 담당자가 소스 코드·터미널·모델 키를 매 실행마다 다루지 않아도 된다. 프로젝트별 인증·데이터 준비는 최초 환경 구성에서 책임자가 연결한다.

### 잘못된 보장 금지

- 같은 테스트를 반복하면 반드시 같은 결과가 나온다는 보장. 실제 제품의 간헐 오류·외부 서비스·시간·네트워크는 달라질 수 있다.
- VM/context를 새로 만들면 서버 데이터·로그인 정책·외부 효과까지 초기화된다는 보장.
- 모든 문서 형식을 완벽히 이해하거나, 모든 앱·모든 OS에서 같은 입력·영상 기능을 제공한다는 보장.
- 같은 OS 사용자가 수정할 수 있는 로컬 파일 hash를 변조 방지 인증으로 표시하는 것.
- 테스트 프로세스 종료·클릭 성공·통과율 하나로 제품 품질 또는 전체 QA 완료를 보장하는 것.

**반복성의 정의:** 동일한 실행 정의와 검증 가능한 시작 조건을 사용한다. 조건이 달라졌거나 복원할 수 없으면 “동일 조건 재실행 불가/비교 불가”로 알린다. 결과 차이는 숨기지 않고 실패·간헐성·환경 차이로 조사한다.

## 3. 누구의 책임인가

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| QA 담당자 | 시나리오/기대값 검토, 필수 대상 선택, 실행·중지, 결과·결함 확인 | 병렬 알고리즘 선택, VM마다 OS 설치, 실행 코드 수동 재작성 |
| 프로젝트/환경 관리자 | 허용 계정·테스트 데이터·origin·준비/정리 도구, 환경 버전·증거 정책, 검증된 동시 상한 | AI 추론만으로 고객 환경 권한 승인 |
| QAutra 실행 엔진 | 검증된 정의·정책에 따른 순서, 자원 소유권, 실행·취소·증거·판정·복구 | 모델 설명만으로 독립성·성공·정리 완료 인정 |
| 선택적 AI | 임의 문서 해석, 시나리오/실행 코드 초안, 근거를 붙인 실패 분석·변경 제안 | 병렬 배치 결정, 실행 중 승인본 변경, 자동 PASS, 임의 재시도·자가 수리 |

로컬 단일 사용자 모드에서 위 역할은 업무 책임 구분이다. 실제 다중 사용자 RBAC가 구현됐다는 뜻이 아니다. 공유/원격 제어를 제공할 때는 인증·역할·감사·동시 편집 제어를 서버에서 집행해야 하며, UI에서 버튼만 숨겨 권한을 구현하지 않는다.

## 4. 제품 사용 흐름

1. **프로젝트 선택:** 기존 URL·앱·환경·테스트 계정 구성을 재사용한다. 이미 연결된 URL을 매번 입력하지 않는다.
2. **시나리오 준비:** 문서 첨부/붙여넣기, 기존 시나리오 선택, QA용 단계 편집기로 작성한다. 외부 AI도 같은 작업 기록에 초안을 제출할 수 있다.
3. **실행 정의 확인:** 원문과 해석, 전제·단계·기대값·필수 환경·데이터 영향을 확인한다. 새/변경 시나리오는 묶음 검토 후 실행 가능한 revision으로 확정한다. 기존 확정본은 매 실행 재승인하지 않는다.
4. **사전 점검:** 실제 환경·초기 데이터·인증·필수 녹화·저장 공간·실행 권한을 확인한다. 부족한 항목은 원인과 해결 경로를 보여 준다.
5. **실행:** 기본 순차로 수행한다. Space에서 현재 단계·실제 대상·관측 시각·녹화 상태를 본다. 입력은 실행기가 소유하며 사용자의 평소 키보드/마우스를 점유하지 않는다.
6. **결과 확인:** 기대값과 실제 결과, 실패 구간 영상, 로그·증거, 필수 미실행 항목을 확인한다.
7. **새 실행 시도:** 같은 확정본·범위·초기 조건으로 재실행한다. 제품 수정 빌드와 비교하면 변경된 빌드를 명시하고 기존 실패를 보존한다.

AI 연결이 없더라도 확정된 실행 정의와 수동 단계 편집은 사용할 수 있어야 한다. 자유 형식 문서의 의미 해석이 AI를 필요로 하는 경우에는 “AI 해석 연결 필요”로 알린다. 파일 업로드만으로 실행 가능 상태가 되는 척하지 않는다. 정확한 의미가 확인되지 않은 기대값만 질문하며 알려진 독립 항목은 준비를 계속할 수 있다.

### Claude 연결 — 구독 CLI 전용

- 최신 사용자 결정에 따라 Claude API key·Console·외부 provider 연결은 제공하지 않는다. 구독 계정으로 로그인한 공식 로컬 Claude Code CLI만 사용한다. 로그인 여부와 구독 인증 방식은 구분하고, API key/helper·Console·외부 제공자·불명확한 인증이면 원문 전송 전에 차단한다.
- QAutra가 OAuth token을 추출·복사하거나 별도 API client로 구독 인증을 재사용하지 않는다. 계정 로그인과 갱신은 공식 CLI가 담당한다. 회사의 managed 정책을 우회하지 않는다.
- 설정에는 `Claude Code · 구독`과 실제 점검 결과를 표시한다. 사용 선호 토글을 로그인·모델 사용 권한·잔여 사용량의 증거로 표시하지 않는다. 사용량·인증 오류에서 API key나 다른 제공자로 자동 전환하지 않는다.
- 원문 전송 동의·미검토 초안·사람의 검토/발행 경계는 유지한다. Claude 연결 없이 수동 작성과 확정본 실행은 가능해야 한다.
- 구독 계정의 Usage credits/추가 사용량이 켜져 있으면 CLI에도 별도 과금이 가능하다. `API 연결 없음`을 `추가 비용 없음`으로 표현하지 않는다. 계정 설정·사용량은 QAutra의 보증 범위가 아니다.

### 검토와 발행의 구분

| 상태 | 의미와 허용 |
|---|---|
| 초안 | 가져온 자료와 작성 중 내용. 정식 회귀 실행 자격 없음 |
| 해석 검토 완료 | QA가 원문·전제·필수 경로·기대값의 해석을 확인. 아직 생성 코드의 실행 허가가 아님 |
| 실행 정의 검증 완료 | 해석한 각 필수 항목이 지원 동작·assertion·조건·권한·고정 코드/의존성에 대응하고 누락/미지원이 없음 |
| 발행된 revision | 위 대응과 검토 기록을 불변 묶음으로 고정. 현재 권한·환경 사전 점검을 통과하면 매회 재승인 없이 실행 |
| 실행 검증 이력 | 실제 실행으로 확인한 대상·조건·결과. 발행 사실 자체가 해당 제품의 PASS나 모든 환경의 실증은 아님 |

QA는 코드 대신 단계와 실제 검증 범위·대상·누락을 검토한다. 생성 후 단계/코드/helper/판정 의미 변경은 새 revision과 영향 검토가 필요하며 기존 발행 자격을 자동 승계하지 않는다. 초안 시험 실행은 별도 표시하고 정식 결과/비교 기준으로 자동 승격하지 않는다.

## 5. 반복 실행의 고정 계약

각 실행은 아래를 실행 시작 전에 고정한 manifest에 연결한다. 이는 내부 기록이며 사용자가 JSON/DSL을 작성해야 한다는 뜻이 아니다.

- 논리 문서 ID·원문 revision/digest·위치, 원 TC ID·내부 지속 ID.
- 시나리오 revision, 필수 단계·assertion·근거, 지원되지 않는 검증 항목.
- 실행 코드·helper·설정·runner/driver 버전, 허용된 조건 분기·readiness·timeout 정책.
- 실제 앱/프런트/API build, feature flag/config, mock/dev/staging 구분.
- 브라우저 binary·OS/runtime·기기 종류·viewport/DPR·언어·시간대·필요한 접근성/IME·권한 조건.
- 테스트 전용 계정 참조, 데이터 초기 상태·준비/정리 버전·소유 ID, 외부 시스템·시간·랜덤 의존성.
- 필수 시나리오×대상, 실행 목적·attempt, 권한과 증거/보존 정책.

schedule 정책 버전·선행 관계·자원 예약 범위도 고정한다. 코드가 같더라도 임의 helper 교체·외부 동적 import·설정 drift가 실행 정의를 바꾸지 못하게 내용과 의존성을 묶는다. 지원 경계 밖의 동적 코드를 결정적 회귀로 발행하지 않는다.

다음 revision과 식별자를 섞지 않는다.

| 용어 | 의미 |
|---|---|
| 문서/시나리오 revision | 원문과 검증 정의의 변경 이력 |
| 작업 공간 revision | 동시 저장 충돌 방지 값. 시나리오 확정/검토의 증거가 아님 |
| 관측 revision·소유권 세대 | 입력 직전 화면과 제어권 유효성. 제품 시나리오 버전이 아님 |
| 실행(run) | 요청한 suite·대상·필수 범위와 그 결과를 모은 기록 |
| 실행 시도(attempt) | 한 독립 흐름을 특정 target·시작 조건으로 수행한 기록. 새 시도는 원 결과를 덮지 않음 |
| Space | 활성 attempt의 관측/증거 UI. worker/기기와 영구 일대일 대응하지 않음 |

고정 가능한 것과 관측만 가능한 것을 구별한다. SaaS backend의 정확한 build를 알 수 없으면 미확인이라고 표시한다. 실제 시간/네트워크/외부 서비스가 요구인 TC를 결정적으로 만들겠다며 mock으로 바꾸지 않는다. 시간 고정·seed·stub이 필요한 경우 승인된 테스트 환경에서만 적용하고 실제 환경 검증과 구분한다.

실행 중 파일 변경은 현재 attempt에 반영하지 않는다. 변경본은 새 revision이다. 안정된 selector·명시적 상태 대기·판정식을 사용하고 고정 sleep이나 임시 화면 ref를 영구 테스트 정의로 저장하지 않는다. 필수 selector가 유일하지 않거나 새 UI에서 맞지 않으면 실패/차단 이유를 보여 주고 변경 초안으로 다룬다.

원문 파싱 전에 시트·표·문단·그림·안내문의 구간 목록을 확보한다. 헤더 없는 첫 행·병합된 공통조건·복수 기대값이 사라지는 문제를 구간별 대조로 검출한다. 불명확한 내용을 그럴듯한 assertion으로 메우지 않는다. 원본의 과거 Result는 참고 이력일 뿐 새 실행 결과가 아니다.

### 여러 문서로 전달되는 TC의 가져오기 계약

- TC JSON과 별도 실행 가이드·기획 근거·과거 이슈 목록을 하나의 입력 묶음으로 연결할 수 있어야 한다. 특정 Excel 양식이나 `tc_id` 같은 필드명을 필수로 하지 않는다. 형식별 구조 추출과 의미 대응 검토를 분리한다.
- 중첩 객체·배열, 알 수 없는 필드, 빈 문자열·빈 객체·`null`, 원 TC ID·분류·근거·회귀 표시는 원본과 정확한 위치에 연결해 보존한다. 원 TC ID와 내부 identity를 구분하고 문서·revision·위치가 다른 동일 ID를 조용히 합치지 않는다.
- 한 TC의 복수 기대값은 각각 검증 대상이다. 쿠키·언어·국가·통화·viewport·mock/dev 조건과 공통 전제는 별도로 연결하고, 현재 화면의 `observed`나 과거 `Result`를 기대값 또는 새 실행 결과로 승계하지 않는다. `result: {}`도 미실행 기록이다.
- 파일의 문법 오류·중간 절단·중복 필드처럼 손실 가능성이 있는 입력은 위치와 원본을 남기고 검토 필요로 둔다. 가이드의 “415행”과 실제 받은 행 수는 별도로 표시한다. 일부 행 수신을 전체 가져오기 완료로 표시하거나 누락 부분을 생성하지 않는다.
- 별도 가이드의 공통 조건은 개별 TC와 명시적으로 연결한다. 여러 TC가 든 원본을 분리할 때 대상 TC·공통 전제·나머지 구간의 처리 범위를 검토하고, 다른 TC의 기대값을 일괄 참고로 바꾸거나 하나의 거대한 상태 의존 흐름으로 강제 변환하지 않는다.
- “기획 확인 필요”, 과거 예상 FAIL, mock 불가, 문서 간 문구 충돌은 원문과 함께 검토 항목으로 보존한다. 자연어 표시만으로 자동 N/A·제외·FAIL을 확정하지 않는다. 판정 기준 미확정과 실행 환경 부족을 구분하고 필수 미실행 범위는 전체 판정에서 숨기지 않는다.
- “새로고침 금지”, “앞 행 직후”, 동일 탭·페이지 메모리 의존은 검토할 상태 의존 관계다. 사용자가 확인한 흐름만 동일 세션·순서로 고정하며 AI가 병렬 실행을 배치하거나 새 context에서 이어받은 척하지 않는다.
- 모바일 UA·viewport 에뮬레이션을 실제 iPhone·Android·Safari 실행으로 표시하지 않는다. OS 공유 시트·기기 설정·접근 불가 API·서버 시간/국가 판정은 해당 관측·실행 capability가 있어야 검증한다.
- 가이드에 포함된 서버 실행·로그인·응답 변조·쿠키·공유 클립보드·포그라운드 전환 명령은 자료이지 즉시 실행 권한이 아니다. 제품의 권한·허용 대상·호스트 입력 비간섭 계약을 그대로 적용하며 호스트 포커스·키보드·클립보드 조작으로 우회하지 않는다.

### 5.1 검증식의 의미와 근거

지원 assertion은 **대상 identity, 관측 표면·범위, 연산/기대값, 필수 표본 수, 관측 시간창·유지 조건, 불완전 관측 처리**를 가진다. 일반 QA 편집기는 이를 이해 가능한 필드로 보여 준다. 실행 엔진이 assertion별 관측·판정 receipt를 생성하고 필수 목록과 대조한다. 실행 코드의 `true` 반환이나 “assertion을 한 번 호출함”은 전체 통과 근거가 아니다.

- 같은 금액이 다른 주문 행에 있어도 지정 주문의 검사로 인정하지 않는다.
- 화면 밖/잘린 트리/접근 불가 iframe·canvas·WebView의 빈 관측은 대상의 부재가 아니다. 빈 매칭 집합의 전칭 검사도 통과로 간주하지 않는다.
- “삭제됨”은 승인된 저장소/화면의 해당 entity 상태로 검증한다. “현재 viewport에 글자가 안 보임”으로 의미를 낮추지 않는다.
- “오류가 발생하지 않음”은 정의된 관측 범위와 시간창에서만 판단한다. 지원되지 않는 시각·업무 판정은 원문을 보존하고 미지원/판단 불가로 남긴다.

### 5.2 실제 프로젝트 권한

시나리오 발행과 위험 동작 권한은 별개다. 환경 책임자가 관리하는 grant는 환경/tenant/계정, 허용 operation, 소유 entity·fixture 범위, 외부 효과와 허용 sink, 유효기간, 정책 버전에 묶는다. 문서·AI·테스트 코드가 grant를 만들거나 확대할 수 없다. dispatch 직전 현재 유효성을 확인한다.

버튼 클릭·Enter·submit·setup/cleanup hook은 같은 효과 경계를 따른다. 테스트 tenant의 승인된 주문이 가능한 것과 실제 결제/발송을 허용하는 것은 다르다. 제한된 계정·테스트 sink 등 프로젝트가 제공하는 집행 수단이 필요하며 버튼 이름/키워드만으로 효과 안전성을 증명하지 않는다. 이 경계를 확인하지 못하면 순차여도 차단한다. 로컬 OS 사용자와 승인된 테스트 코드의 신뢰 경계를 악성 코드 sandbox 보장으로 확대하지 않는다.

### 5.3 실제 조건과 비교

manifest의 선언값과 실행 중 관측값을 분리한다. 사전 점검, 관련 흐름 경계, 최종 집계에서 build/config·fixture·권한 등 확인 가능한 조건을 검사한다. 중간 HMR·API 배포·flag drift가 확인되면 변경 구간과 영향을 남기고 서로 다른 build의 결과를 하나의 동일 build 전체 PASS로 합치지 않는다. 관측할 수 없었던 값은 동일하다고 추정하지 않는다.

fixture의 실제 소유 ID와 승인된 시작 상태의 동등성을 구분한다. 새 fixture ID라도 사전 정의한 동일 상태일 수 있고, 같은 ID라도 내용이 다르면 동등하지 않다. 비교에서 제외할 생성 ID·시간값은 실행 전에 정하며 결과가 나온 뒤 유리하게 제외하지 않는다. 차이가 있는 실행은 변경 조건 비교로 보존하고 동일 조건 재현/미재현과 구분한다.

## 6. “테스트마다 브라우저/기기 하나”의 정확한 단위

**권고 단위는 ‘독립 실행 흐름 × 대상 환경 × 실행 시도’다. TC 한 행·클릭 한 번·Space 카드 한 장이 아니다.**

- 독립 실행 흐름은 필요한 초기 상태부터 검증·정리까지 묶인 시나리오 또는 상태 의존 chain이다.
- 예: “등록 → 목록 반영 → 수정 → 재진입 유지”가 같은 상태를 이어야 하면 한 세션/기기를 유지한다. 문서에 네 TC로 나뉘어 있어도 네 브라우저로 쪼개지 않는다.
- 독립된 다음 시나리오는 새 격리 세션 또는 확인된 초기화 상태에서 시작한다.
- 하나의 흐름이 팝업·여러 탭·두 사용자 동작을 검증하면 그 정의에 맞는 복수 페이지/자원을 하나의 소유 묶음으로 예약한다. “브라우저 하나”를 literal window 1개 제한으로 만들지 않는다.
- 실제 여러 기기 간 동작이 요구된 TC는 복수 기기를 원자적으로 예약한다. 단순 TC 병렬화와 구분한다.

원 TC는 추적 단위이고 chain은 실행·초기화 단위다. 작성 화면에서 TC의 선후 관계와 상태 인계를 QA가 검토·확정한다. 후행 TC만 선택하면 필요한 선행 범위와 변경 효과를 시작 전에 보여 주고 함께 선택하도록 하거나, 독립 실행 불가 사유를 표시한다. 엔진이 앞 단계를 몰래 추가하지 않는다.

선행 PASS가 필요하거나 같은 상태를 이어야 하는 후행 항목은 선행 FAIL/unknown/세션 상실 시 차단되고 사유를 원 TC별로 남긴다. 단순 순서만 있는 독립 항목은 확정된 실패 후 계속/중단 정책을 따른다. 기본 재실행은 검증된 시작 상태에서 **새 chain attempt 전체**이며 중간 재개는 별도로 검증된 checkpoint가 없으면 제공하지 않는다.

두 사용자 채팅 TC의 `발신자 Chrome + 수신자 Safari`는 역할별 target/session/증거를 가진 하나의 공동 attempt다. 반면 같은 TC를 Chrome과 Safari에서 각각 검증하는 matrix는 두 독립 attempt다. UI는 공동 흐름의 전체 판정과 역할별/원 TC별 결과를 함께 표시한다.

| 대상 | 흐름 동안 배타 할당 | 흐름 사이 재사용 | 주의 |
|---|---|---|---|
| 웹 Chrome | 독립 context/profile과 그 페이지 묶음. 필요 기능/장애 경계에 따라 전용 process | worker/프로세스는 검증된 초기화·상태 분리 조건 아래 재사용 | 새 탭만으로 쿠키·서버 데이터 격리 안 됨. 공유 process crash는 복수 흐름에 영향 |
| 실제 desktop Safari | 지원되는 실제 Safari automation session과 필요 desktop 사용권 | 준비된 macOS worker를 순차 재사용, 종료·초기 상태 확인 | 같은 환경의 Safari WebDriver 슬롯 제한. WebKit 대체 금지 |
| Android/iOS | 선택한 emulator/simulator/실기기 전체와 driver session | 전용 기기 풀에서 초기 상태 검증 후 재사용 | 앱 재실행·재설치·기기 초기화의 효과가 다름. 서버 데이터·keychain/권한 별도 |
| 복수 사용자/기기 TC | 명시한 여러 자원을 하나의 흐름에 예약 | 각 자원 정리·종료 확인 뒤 반환 | 자원 일부만 잡고 무한 대기 금지 |

OS·VM·에뮬레이터를 테스트마다 새로 설치하지 않는다. 준비된 자원 풀을 재사용하되 **따뜻하게 켜져 있음과 깨끗한 테스트 상태는 다르다.** 초기 상태를 확인할 수 없는 자원은 격리한다. 개인 브라우저 프로필·개인 기기를 자동 채택·초기화하지 않는다.

초기화의 확인 범위는 앱 재실행/앱 데이터/권한/keychain/OS/서버 fixture로 나눈다. Appium `fullReset`은 driver별 의미이며 기기 공장 초기화가 아니다. Android Quick Boot는 종료 상태를 저장할 수 있으므로 clean baseline으로 자동 인정하지 않는다. 명시적으로 관리하는 snapshot도 OS/runtime/config가 바뀌면 무효화될 수 있고 서버 상태는 되돌리지 않는다. `-wipe-data`도 외부 SD image까지 모두 지우는 뜻이 아니다. 최초 설치·업그레이드·IME·animation TC에는 driver의 자동 설정 변경도 실행 조건으로 기록한다.[S3–S6]

Appium의 `NATIVE_APP/WEBVIEW` context 전환은 같은 기기의 제어 대상을 바꾸는 기능이다. 웹 BrowserContext의 저장 상태 격리와 다른 용어로 설명한다. 실기기·시뮬레이터마다 reset/권한/녹화 기능이 같다고 가정하지 않는다.

충돌 범위는 `page/context → browser process → worker desktop → host 공유 서비스`의 상위 관계를 포함한다. OS dialog·GUI 입력·IME가 필요한 흐름은 시작 전 필요한 desktop 범위까지 예약한다. 선언하지 않은 GUI 경로가 나타나면 다음 변경 dispatch를 막고 준비/정의 변경 필요로 종료한다. 실행 중 자원 범위를 몰래 넓히거나 host-global 입력으로 fallback하지 않는다.

다른 Simulator·개인 창·공유 ADB/Appium/CoreSimulator 서비스를 일괄 종료/초기화하는 옵션은 정상 준비·정리 수단으로 허용하지 않는다. driver 설정을 기록했다는 사실은 사용 허가가 아니다. 소유한 대상과 제한된 helper만 조작하며, 플랫폼상 전역 효과를 피할 수 없는 기능은 전용 환경 없이는 미지원으로 둔다.

## 7. VM 중심과 Space 중심 비교

VM은 실행/격리 기술이고 Space는 사용자에게 실행을 보여 주는 방식이다. 둘 중 하나만 선택해야 하는 관계가 아니다.

| 대안 | 장점 | 단점·위험 | 제품 영향 | 판단 |
|---|---|---|---|---|
| 테스트마다 새 VM·모바일 OS | OS 초기 상태/장애 경계를 강하게 분리할 수 있음 | 부팅·설치·메모리·디스크·라이선스 비용. backend 상태까지 초기화하지 않음 | QA가 인프라를 관리하는 UX가 되기 쉬움 | 기본 채택 안 함. 격리가 필수인 제한된 작업만 |
| Ego형 자체 임베디드 브라우저를 제품 중심으로 개발 | 가벼운 다중 화면·직접 조작 UX에 유리 | 브라우저 배포/보안 업데이트 비용. Chromium이라고 실제 Chrome/Safari가 되는 것 아님 | 제품이 QA 도구에서 브라우저 개발로 커짐 | UX만 참고. 브라우저 fork는 기본 채택 안 함 |
| Space UI + 준비된 worker/기기 풀 | QA 흐름을 통일하고 자원은 종류별 재사용. 설치와 실행 분리 | backend별 제약·영상·상태 초기화·복구 구현 필요 | 기존 엔진/드라이버 재사용 가능, UI에서 실제 상태 계약 필요 | **권고** |
| 외부 기기/브라우저 서비스 중심 | 환경 운영·버전 공급 부담을 줄일 수 있음 | 비용·계정·사내망·고객 데이터 반출·서비스 장애·embed 권리 | 별도 승인과 공급자별 기능 검증 필요 | 선택 연결. 기본 필수 아님 |

### 권고 backend 배치

- Chrome: 기본은 기존 QAutra 전용 worker에서 브랜드/버전이 확인된 Chrome과 흐름별 새 context를 사용하는 방향이다. 소수의 준비된 worker를 재사용하며 TC마다 VM을 생성하지 않는다. 전용 host headless/process 경로는 추가 대안이지 현재 guest-only 경계를 자동 완화하는 기본값이 아니다. 채택하려면 OS 격리 요구 변경을 명시적으로 승인하고 비간섭·capture·지원 기능을 검증해야 한다. Linux Chrome 결과는 macOS Chrome 결과가 아니다.
- Safari: 준비된 로컬 macOS guest 또는 사내 전용 Mac에서 실제 Safari를 실행한다. 기본 QA 사용자는 “Safari 사용 가능/준비 필요/대기”만 본다. 최초 OS·권한 준비는 관리 화면으로 분리한다. 사용자 host Safari 권한을 바꿔 우회하지 않는다.
- 모바일: 전용 Android/iOS 인스턴스 풀을 사용한다. 실기기·emulator·simulator를 명확히 표기한다. iOS Simulator를 실기기 iPhone으로 표시하지 않는다. 실제 지원 여부는 경로별 검증 전에는 준비 필요/미지원이다.
- Docker는 Linux worker 구성 선택이지 실제 macOS Safari의 대안이 아니다. macOS에서 Docker Desktop 자체의 VM과 설치·권한 부담도 고려해야 한다.

Chrome의 비-VM 경로는 현재 guest-only desktop 코드에서 변경이 필요한 후보다. 같은 Space UI를 쓴다고 새 backend가 이미 지원된 것으로 보이지 않게 한다. 브라우저 process/desktop별 캡처 범위·OS dialog·IME 지원과 포커스 비간섭을 첫 대상 실증에서 확인한다.

## 8. AI 없는 실행 순서 결정

### 기본

- 일반 QA 화면에는 “AI가 병렬 판단”, “에이전트 수”, “최대 속도 자동 배치”를 두지 않는다.
- 기본 작업 공간 동시 실행 상한은 1이다. 이 기본값은 처리량 보장이 아니라 보수적 시작값이다.
- 기본 순서는 확정된 suite/chain 순서다. 여러 요청은 접수 순서와 명시적 우선순위를 따르며 대기 이유를 표시한다.
- 상태 의존 흐름은 같은 session/lease를 유지한다. 단순 순서 의존, 선행 PASS 의존, 상태 인계를 구별한다.

### 관리자 검증 뒤 허용하는 제한적 동시 실행

AI 없이도 엔진이 다음 사실을 검증할 수 있을 때만 허용한다.

- 실제 target/기기/port 및 필요한 worker GUI 소유권이 겹치지 않음.
- 계정뿐 아니라 backend/tenant/재고/주문/fixture/reset·cleanup 영향이 독립임.
- 프로젝트의 신뢰된 준비 도구가 고유 데이터를 발급하고 정리 범위를 증명할 수 있음.
- 메모리·디스크·부팅·녹화 부하와 플랫폼별 실제 상한 안에 있음.
- 필요한 복수 자원의 예약과 crash 뒤 복구를 같은 관리자가 집행함.

동일 backend의 URL 별칭과 상하위 충돌 키를 정규화한다. AI나 TC 문자열이 충돌 범위를 축소할 수 없다. 알 수 없는 효과는 병렬 안전으로 추정하지 않으며, 순차여도 초기 상태·권한을 알 수 없으면 차단한다. 여러 Mac이 공유 backend를 쓰는 경우 로컬 잠금만으로 전역 배타성을 보장하지 않는다. 공유 예약 서비스가 없으면 프로젝트 제공 독립 fixture namespace로 검증되거나 해당 공유 실행은 지원하지 않는다.

동시 실행은 기본 작업 흐름의 필수 설정이 아니다. 프로필 등록 수·준비된 자원 수·실제 실행 수·관리 상한을 별도로 표시한다. 설정값을 저장하는 것과 엔진에서 집행하는 것을 혼동하지 않는다.

UI·CLI·MCP·SDK·direct script가 같은 admission·quota·효과 예약을 통과한다. runner 내부 플랫폼 fan-out이나 script의 `Promise.all`도 이 경계를 넘지 못한다. “기본 1”은 단일 화면/프로세스 설정이 아니라 **독립 흐름의 활성 실행 상한**이며 한 흐름이 요구하는 복수 기기 예약은 별도 자원 상한 안에서 처리한다. 자원 소유권은 작업 공간이 달라도 같은 실행 자원에 대해 단일 권위로 관리한다. 모델은 dependency/충돌 계약을 제안하거나 확정하는 권한이 없으며, 가져온 문서의 관련 문구는 검토할 자료일 뿐이다.

상한은 **프로젝트 정책 + 로컬 사용자 전체 관리 상한 + worker/host의 자원 예산 + 플랫폼 실제 제한**을 모두 만족해야 한다. 기본 순차 상한 1은 로컬 사용자 전체에도 적용하며 프로젝트를 나눠 우회하지 못한다. 별도 Mac은 공유 backend의 계약을 별도로 만족해야 한다. 모든 설정에는 적용 범위를 표시한다.

독립 흐름의 실행 상한은 준비 시작부터 진단 보존·정리/필수 증거 저장 완료까지 점유한다. 부팅 중·warm idle의 VM/기기는 실행 건수와 별개로 실제 CPU/RAM/디스크/기기 상한에 계속 계산한다. 상한을 낮추면 신규 배정을 제한하고 기존 작업은 안전하게 drain하며 강제 종료하지 않는다.

접수 순서·명시 우선순위에 readiness와 자원 반환 사건을 더해 배정 이유를 기록한다. 우선순위별 공정한 대기와 오래 기다린 작업의 보호 규칙을 고정 정책으로 제공하며, AI가 순서를 바꾸지 않는다. 두 checkout·UI/CLI의 요청도 같은 자원 권위/전체 예산을 우회할 수 없어야 한다.

## 9. 실행 상태·판정·복구 계약

### 실행 상태

`준비 중 → 대기 → 실행 중 → 정리/증거 저장 중 → 완료`를 기본으로 한다. 별도 분기로 `확인 필요`, `중지 요청 중`, `중지됨`, `복구 필요`를 둔다. 전송 중 명령이 있을 때 중지 버튼을 눌렀다고 즉시 “안전하게 중지됨”으로 표시하지 않는다.

- 대기 취소: 시작하지 않았음을 확인하고 취소한다.
- 실행 중지: 새 입력 차단 → 진행 명령의 효과 확인 → 안전한 소유 자원 정리/영상 확정 → 최종 상태 기록.
- 권고 UX는 **창 닫기에는 실행 유지, 명시적 앱 종료에는 진행 작업 안내와 안전 중지·정리**다. 종료 대화상자의 기본은 `계속 실행`이며, `중지 후 종료`는 정리 완료 뒤 종료한다. 종료/업데이트 요청 중에는 새 실행을 받지 않는다. 구현에서 지원하기 전에는 백그라운드 실행 완료로 안내하지 않는다. 강제 종료·OS 종료·실행기 crash는 이 안전 종료를 보장하지 않으므로 재접속 시 durable 기록·소유권을 확인하고 불명확한 작업은 복구 필요로 남긴다.
- 연결 단절·OS sleep·디스크 부족·worker crash 뒤에는 마지막 journal과 소유권 세대를 확인한다. 변경 명령을 자동 재전송하지 않는다.
- lease 만료나 시간 경과만으로 dirty 자원을 clean 상태로 돌리지 않는다. 복구에는 실제 종료·초기화/데이터 상태 확인이 필요하다.

### 중지와 진단 보존

- `중지 후 정리`: 일반 중지다. 자원·영상 정리가 끝나면 화면은 저장 증거로 전환한다.
- `자동 실행 종료 후 진단`: 아직 보존 가능한 실행에 한해 신규 dispatch 차단 → 진행 명령 효과 확인 → 자동 회귀 종료/개입 기록 → 진단 전용 제어로 전환한다. 원 attempt의 무인 실행으로 돌아가지 않는다. 효과가 unknown이면 직접 변경을 열지 않고 읽기 전용 관측과 복구 안내만 제공한다.
- 진단 보존 동안 worker/계정/fixture 소유권과 용량 점유를 유지한다. 권고 기본 보존 시간은 10분이며 성능 실측값이 아닌 제품 정책이다. 남은 시간·`10분 연장`·`진단 종료 및 정리`를 표시하고 만료 시 신규 진단 입력을 막아 안전 정리한다. 창을 닫아도 기한은 유지하고 명시적 앱 종료는 같은 안전 종료 흐름을 따른다.
- 이미 정리된 실행의 실패 화면은 다시 살아 있는 session으로 만들지 않는다. 저장 증거를 보거나, 검증된 초기 상태의 별도 진단 실행을 요청한다. 그 결과를 원 회귀 결과로 대체하지 않는다.
- Safari native takeover로 단절된 WebDriver는 재연결 가능한 pause로 표시하지 않는다. 새 자동 실행은 새 session/attempt가 필요하다. 진단 중 crash/단절/기한 만료도 종료·cleanup이 확인되기 전에는 자원을 반환하지 않는다.
- recorder 최종화가 context 종료를 요구하는데 보존과 양립하는 검증된 녹화 경로가 없다면 해당 환경의 진단 보존을 비활성화한다. `영상 저장을 위해 실행 환경 종료 필요` 사유와 읽기 전용 Replay를 제공한다.

### 복구와 자료 복원

원 unknown 판정과 자원 복구를 분리한다. client/driver를 닫고 현재 조회가 깨끗하다는 사실만으로 지연된 backend 작업의 종료를 증명하지 못한다. 알려진 비동기 작업·변경 효과의 종료/격리 근거가 있어야 영향 범위를 재사용한다. 이를 확인할 수 없으면 범위를 계속 격리하거나 영향이 겹치지 않는 새 fixture를 준비한다. 이후 복구됐어도 원 unknown을 PASS로 바꾸지 않는다.

읽기 전용 상태 조회의 재시도, dispatch 전의 준비 재시도, 새 attempt, setup/cleanup 재호출은 서로 다른 정책이다. hook도 변경 효과가 있으면 응답 유실 뒤 자동 재호출하지 않는다. 복구 화면에는 확인 항목·담당자·검증 결과를 보여 주고 journal 수동 편집을 요구하지 않는다.

backup 복원은 외부 효과의 롤백이 아니다. migration/rollback/restore는 request identity·완료/unknown 이력·소유권 세대·quarantine·grant를 함께 다루며 외부 현황과 대조하기 전 dispatch를 재개하지 않는다. 복원된 과거 대기 작업을 자동 재실행하지 않는다. 구버전은 이해하지 못하는 실행 schema를 거부하거나 읽기 전용으로 열고 원본을 유지한다.

### 결과의 여러 축

| 축 | 사용자에게 보여 줄 사실 |
|---|---|
| 업무 판정 | 기대값 충족, 실제 불일치, 판단 근거 부족 |
| 실행 상태/원인 | 실행 전 차단, 도구 오류, 중단, 변경 결과 미확인, 미실행 |
| 증거 | 영상/화면/로그 준비, 저장 중, 불완전, 만료/삭제 |
| 정리 | 완료, 실패, 상태 미확인·재사용 금지 |
| 비교 | 동일 조건 재현/미재현, 변경 조건 비교, 비교 불가, 간헐 결과 근거 |

전체 PASS는 비어 있지 않은 사전 필수 범위의 모든 필수 검증이 통과하고 필수 증거·정리·실행 확실성 조건을 충족할 때만 표시한다. 일부 PASS, 필수 skip·누락·검증 단계의 수동 대체·필수 영상 실패를 통과율로 감추지 않는다. 선택적 로그 하나의 실패를 업무 결함으로 바꾸지 않는다. 사전에 선언한 MFA/로그인 준비의 사람 참여는 그 사실과 시점을 기록하며, 로그인 UI 자체가 검증 범위가 아니라면 이후 자동 검증의 PASS를 무조건 막지 않는다. 필수 사용자 경로 중간의 사람 개입은 무인 회귀 PASS로 표시하지 않고 원 attempt를 중단/개입 이력으로 보존한다.

업무 deadline 위반과 도구 timeout은 구별한다. unknown은 FAIL로 원인을 지어내거나 자동 PASS로 복구하지 않는다. 원래 FAIL 뒤 정리 실패가 나면 두 원인을 모두 보존한다. 재시도는 별도 attempt이며 원 실패를 지우지 않는다. 변경되지 않은 조건의 반복 결과가 갈릴 때만 간헐성 근거로 분류한다.

## 10. 실패 영상과 리포트

- 사전에 정한 필수 영상 범위의 첫 동작 전에 올바른 capture source의 준비와 첫 유효 frame을 확인한다. 앱 launch/OS dialog 자체가 검증 범위면 그 이전 화면부터 잡을 수 있는 경로가 필요하다. page 영상만 가능한 경로를 desktop/launch 영상이라고 표시하지 않는다. 필요한 범위를 수집할 capability가 없으면 실행 전 차단한다.
- 녹화는 실행 수명주기에 묶는다. 수동 녹화 버튼을 눌러야 실패 영상이 남는 제품이 아니어야 한다.
- 장시간 녹화·중간 crash를 위해 복구 가능한 segment를 확정하고 action 순서·시간축·누락 구간과 연결한다. 프레임 존재·파일 크기만으로 정상 영상이라 판단하지 않는다.
- 필수 녹화 상실 시 **현재 흐름을 포함한 다음 변경 dispatch부터** 막고 이미 실행한 효과와 안전 정리를 확인한다. 이미 확인한 제품 FAIL은 유지한다. 단순 live preview 단절과 recorder 실패는 별개다. 유효한 실행 관측·필수 녹화는 유지되고 미리보기만 끊겼다면 실행을 자동 실패로 바꾸지 않고 관측 지연을 표시한다.
- 업무 실패뿐 아니라 실행 중단·infra 장애·증거 불완전 기록도 보존한다. 정상 영상 삭제는 최종 판정·필수 정리·증거 확정 뒤 프로젝트 정책에 따른다.
- 재생은 읽기 전용이다. “영상 다시 보기”와 “테스트 다시 실행”을 다른 버튼·권한·확인 흐름으로 둔다.
- 리포트에는 원 TC ID, 기대/실제, 정확한 환경·build·시나리오 revision·attempt, 실패 시각/영상 구간, 미실행·제약·정리 상태를 넣는다. 실행 시점 스냅샷으로 과거 리포트를 재생성한다.
- export는 휴대 가능한 HTML/결과 데이터/허용된 증거 묶음을 제공하는 방향이다. Excel 등 기존 팀 형식 변환은 원 상태·사유를 손실 없이 매핑하며 특정 workbook을 표준 입력으로 강제하지 않는다.
- raw 파일·redacted 공유본·AI 전송 자료를 구분한다. 개인정보 마스킹 스위치 하나로 모든 화면·영상이 안전해졌다고 표현하지 않는다.

영상의 source capture 순서/시각과 수신 시각을 구별하고 action sequence와 연결한다. 시계 차이·전달 지연·역순·segment 공백을 표시하며, 최근 수신 시각만으로 live라 하지 않는다. 정상 정지 화면과 capture 중단을 지원 경로의 heartbeat/sequence로 구분할 수 없으면 관측 신뢰도 미확인으로 남긴다. 재생 가능한 파일도 실패 시점의 화면을 놓쳤으면 불완전한 증거다.

삭제 범위에는 QAutra가 관리하는 원본·썸네일·임시 segment·worker spool·진단 묶음·backup 정책을 포함한다. 이미 관리 밖으로 export한 복사본은 원격 삭제 보장 대상이 아니다. AI 전송/export 시 현재 유효한 정책을 다시 검사하고 과거 수집 동의를 전송 허가로 재사용하지 않는다. 삭제/동의 철회를 restore로 취소하지 않으며, 실패 기록은 남기고 증거는 삭제됨/삭제 확인 필요로 표시할 수 있다.

### 대상별 capture 계약

아래는 adapter가 충족해야 하는 설계 조건이다. QAutra 통합·실시간 화면·영상 완전성은 이번에 실행 검증하지 않았다.

| 실행 대상 | 필수 capture 범위 | 시작·최종화·회수 조건 | 진단 보존 제약 |
|---|---|---|---|
| 웹 page | 시나리오가 요구한 모든 역할·page/popup. 생성 즉시 관련 입력 전 capture 연결 | page/segment마다 attempt·역할·시각 귀속. context close가 필요한 recorder는 종료→저장/회수→검증 후 보관 완료 | 종료와 녹화 확정이 결합되면 같은 session 보존 불가 |
| 실제 Safari·OS 연동 웹 | viewport만 요구하는지 주소창/OS prompt까지 필요한지 구분. 후자는 소유 desktop/guest capture 필요 | WebDriver screenshot을 연속 desktop 영상으로 대체하지 않음. 실제 recorder readiness·중지·segment 저장/회수를 각각 확인 | glass pane 단절·GUI 소유권·영상 최종화 제약 표시 |
| 모바일 | 요구한 기기 역할 전체의 화면·방향·필요한 native/WebView 전환 | driver별 길이/segment·녹화 시작/종료·파일 회수·재생 검증. audio는 별도 지원 항목 | 기기/session을 닫아야 하는 경로와 계속 관측 가능한 경로 구분 |

live feed·저장 영상·스크린샷·오디오는 서로 다른 capability다. 두 사용자/복수 기기 흐름에서 한 화면만 녹화하고 전체 흐름의 실패 영상 완료라고 표시하지 않는다. 알려진 실패가 recorder가 포착하지 못하는 화면에서 발생하면 업무 결과와 증거 부족을 함께 남긴다.

## 12. Open Design: 정보 구조와 화면별 작업

### 유지할 시각 기반

- 제품명 **QAutra**, 사용자가 제공한 앱 아이콘을 유지한다. 더 이상 가칭으로 표시하지 않는다.
- 제공 `qautra-design-package.zip`의 밝은 shell·왼쪽 navigation·공통 컴포넌트·색/간격 토큰을 출발점으로 삼는다. 디자인 파일은 실제 엔진 동작 증거가 아니라 프로토타입이다.
- 기존 토큰: sidebar 228px, 일반 본문 16px, compact 13px, 보조 metadata 11px, heading 28px, control 40px, 기본 8px 간격, primary `#4266e8`, radius 12px/8px. 필요 조정은 공통 token으로 제안하고 화면별 임의 CSS를 복제하지 않는다.
- 11px 보조 metadata는 원시 ID 등에만 사용한다. 오류·대기 사유·검토에 필요한 본문은 작게 숨기지 않는다.

### 권고 navigation

`실행 현황 / 시나리오 / 요구사항 추적 / 환경 및 기기 / 리포트 / 증거 보관함`, 하단 `설정`을 유지한다. 새 VM 전용 메뉴·AI 작업 큐를 주 navigation으로 올리지 않는다. 프로젝트는 shell 공통 선택이다.

| 설정/진단 | 연결·권한·보존·지원 정보·선택적 AI 작성 도구, 고급 자원 상한 | 저장만 되는 설정을 집행 기능으로 표현 금지. 외부 전송 기본 금지 |

### 버튼과 문구 변경

- `AI 요청 확인`을 제품 공통 주 CTA로 쓰지 않는다. `새 실행`, `시나리오 가져오기`, `검토 필요`를 문맥별로 사용한다.
- `AI에 반환` 대신 `자동 실행에 반환`도 무조건 제공하지 않는다. 일반 회귀 실행은 자동 입력 전용이다. 직접 조작이 필요하면 `실행 중단 후 진단`으로 전환하고 개입 기록을 남긴다. 준비 단계의 승인된 MFA/로그인 인계는 별도 상태로 설계한다.
- `자동 수정 후 재실행` 기본 버튼을 없앤다. `변경 제안 보기 → 새 revision 검토 → 새 실행`으로 분리한다.
- `인스턴스 생성`은 환경 관리자용 고급 동작이다. QA의 기본 버튼은 `환경 선택/점검`이다.
- raw run ID를 화면 제목으로 쓰지 않는다. 실행 이름·형식화한 시각을 우선하고 ID는 보조/복사 기능으로 둔다.
- “완료” 하나로 PASS를 표현하지 않는다. “실행 종료 · 실패 1건 · 영상 저장 완료”처럼 사실을 분리한다.

### 디자인 상태 세트

정상 화면만 만들지 않는다. 각 관련 화면에 빈 상태, 로딩, 권한 없음, 연결 끊김, 데이터 오래됨, 부분 성공, 검토 필요, 자원 대기, 미지원, 취소 요청 중, 복구 필요, 영상 저장 중/불완전/만료, 정리 실패를 포함한다. 위험 동작에는 취소 결과와 재진입 상태도 설계한다.

### 화면 이동과 command 계약

실행 상세가 run/attempt의 중심 화면이다. Space 목록은 그 실행의 관측 모드, Replay는 선택 attempt의 읽기 전용 증거, 비교는 명시적으로 고른 두 attempt의 조건/결과 대조다. 아래 route는 디자인 식별자이며 현재 구현된 HTTP endpoint라는 뜻이 아니다. 상태 재조회와 업무 재실행을 같은 `다시 시도` 버튼으로 묶지 않는다.

| 화면/소유 대상 | command | 전제조건 | 진행 → 성공/실패 | 재진입/취소 |
|---|---|---|---|---|
| `scenario/:id/revision` · 초안 | `검토 후 발행` | 해석·지원 동작/assertion·권한 대응·고정 실행 묶음 검증 | 확정 중 → 발행 revision / 검토·지원 필요 | 편집 취소는 초안 유지, 기존 발행본 불변 |
| 같은 화면 · legacy 항목 | `변환 내용 검토` | 원본 보존·변환 가능성 표시 | 새 초안 → 검토/미지원, 자동 발행 없음 | 기존 기록 조회 가능, legacy를 정식 실행하지 않음 |
| `run/new` · 실행 요청 | `실행 시작` | 발행본·chain 선택 범위·현재 권한·환경·필수 영상 점검 | 요청 등록/대기 → 배정 / 실행 전 차단 | 같은 request ID 조회, 중복 전송은 새 실행 아님 |
| `run/:id` · 미배정 요청 | `대기 취소` | 아직 준비·dispatch 시작 전 | 취소 요청 → 미실행 취소 / 이미 시작이면 중지 흐름 안내 | 재진입 시 서버 상태, 이미 시작한 작업을 미실행으로 표시 금지 |
| `run/:id/attempt/:id` · 활성 시도 | `중지 후 정리` | 소유 실행 | 중지 요청 → 정리/저장 → 중지됨 / 복구 필요 | 화면 닫아도 처리 상태 보존, 업무 자동 재전송 없음 |
| 같은 화면 · 보존 가능 시도 | `자동 실행 종료 후 진단` | 효과 확인·지원 capture/제어·소유권 | 자동 종료 → 진단 보존 → 종료/정리 / 복구 필요 | 남은 기한 유지, 원 무인 attempt로 복귀 없음 |
| `environment/:id/recovery` · unknown 자원 | `복구 상태 확인` | 해당 자원 조회 권한 | 읽기 전용 대조 → 확인됨 / 확인 필요 | 실제 변경 없음, 원 unknown 판정 유지 |
| 같은 화면 · 소유 자원 | `허용된 초기화` | grant·효과 확인·초기화 범위/영향 표시 | 준비/정리 중 → 후조건 확인 / 실패·unknown 격리 | 취소는 진행 효과 확인 후, 응답 유실 시 재호출 금지 |
| 실패 상세 · 원 attempt | `새 실행` | chain 시작 상태·현재 권한 확인 | 범위/변경 조건 확인 → 새 request/attempt | 이전 실패/영상 불변, 원 화면으로 취소 복귀 |
| `run/compare` · 두 attempt | `비교` | 두 기록 선택 | 조건 대조 → 동일/변경 조건/비교 불가 | 읽기 전용, 원 실행으로 이동 가능 |
| `evidence/:id` · 증거 | `내보내기` | 현재 공유 정책·최종화 상태·범위 확인 | 묶음 생성 → 완료 / 일부 불가·실패 | 재진입 시 생성 결과/누락 표시, 외부 전송 자동 재시도 없음 |

로컬의 QA/관리자 표시는 업무 책임 안내다. 실제 인증/권한 집행이 없는 역할 전환 스위치로 접근 통제가 있는 척하지 않는다. `복구 필요`, `정리 실패`, `legacy 검토 필요`, `영상 만료` 각각의 주 CTA·비활성 사유·복귀 위치를 프로토타입에 포함한다.

## 13. Open Design 산출물 요구

이 문서와 사용자가 제공한 원본 `qautra-design-package.zip`을 함께 전달한다. 이전 대화는 필요하지 않다. 아이콘·공통 token/component 자산은 원본 패키지에서 가져오고 별도 제품 로고를 새로 만들지 않는다. 다음을 한 패키지로 제공한다.

전달 묶음에는 원본 ZIP의 파일명·크기·SHA-256과 문서별 SHA-256을 `handoff-manifest.json`으로 포함한다. 원본 ZIP은 내용 수정 없이 동봉하고 `COMPONENTS.md`, `design-tokens.json`, `ui/{tokens.css,components.css,components.js,examples.json,manifest.json}`, `assets/icons/`를 입력 원본으로 명시한다. 개인 Downloads 경로는 조사 이력일 뿐 수신자의 설치 경로 요건이 아니다.

1. 제품 흐름과 navigation, 기존 화면에서 유지/수정/삭제할 항목 목록.
2. §12 화면과 상태별 desktop 시안, 좁은 창·일반 창·넓은 창에서의 배치 규칙. 검수 viewport는 1024×768, 1440×900, 1920×1080 CSS px로 제안한다. 이는 고객 하드웨어 지원 확정값이 아니라 디자인 검수 조건이다.
3. 문서 가져오기→검토/확정→환경 점검→실행→실패 영상→새 attempt 비교의 클릭 가능한 프로토타입.
4. keyboard focus 순서·비활성 이유·empty/error/loading·모달 취소/복귀 명세.
5. 공통 component/token 변경표. 제공 패키지의 `ui/tokens.css`, `ui/components.*`, `ui/examples.json` 방식처럼 공통 원본을 기준으로 한다.
6. 화면별 표시 데이터와 사용자 command, 가능/미지원 상태, 성공/오류 전이. API가 없는 버튼은 실제 지원으로 가장하지 않고 디자인 예시로 표시한다.
7. 샘플 자료에는 정상/제품 FAIL/환경 차단/unknown/영상 불완전/cleanup 실패/조건 차이 비교를 포함한다. 예시를 실제 검증 결과처럼 보이지 않게 한다.

범위 밖: 이번 작업에서 제품 코드 수정, 실제 VM·기기 생성, 개인 설정/권한 변경, 고객 데이터 입력, 실제 AI/provider 연결·테스트 실행. 디자인 handoff를 구현 승인으로 해석하지 않는다.

### Jev와 AI 실행 경로의 중요한 전환

현재 legacy DSL은 일부 동작의 Jev commit/grounding을 요구하고, B02 직접 경로는 합성 fixture 권한에 한정된다. 따라서 “AI 실행 판단 폐지”를 `allowRisky` 전역 설정이나 모델 응답 위조로 구현해서는 안 된다. 확정 시나리오에서 결정적으로 식별 가능한 대상·허용된 작업·프로젝트 효과 계약을 검사하는 경로로 전환하고, 그 경로가 증명되지 않은 동작은 실행 불가로 남긴다.

기존 실행 파일은 원본을 보존하고 변환 가능/검토 필요/현재 미지원으로 분류한다. legacy 실행을 모델 없는 반복 회귀라고 표시하지 않는다. 새 기본 경로 cutover 시 관련 호출자·설정·문서를 함께 변경하고, 같은 일을 하는 숨은 두 번째 runner를 만들지 않는다. 과거 기록 읽기 호환과 과거 위험한 실행 동작 유지 의무는 다르다.

현재 실행 제한 없는 `source.status`를 새 발행 자격으로 승계하지 않는다(`src/spec/load.ts:103-156`). 이미 `approved`였던 파일도 새로운 model-free·scope·evidence 계약의 검증 없이 발행본으로 승격하지 않는다. queued file path 대신 불변 내용 reference를 사용한다. 과거 summary/manifest에 없던 target/build/attempt 정보를 현재 설정으로 채워 넣지 않는다. 설정 화면의 보존 기간도 현재 미집행 값이므로 자동 삭제를 도입할 때 별도 고지·확인이 필요하다.

현재 Mac build는 checkout 경로에 연결된 Debug/ad-hoc 경로이고 앱이 Node 엔진을 시작한다(`scripts/build-mac.sh:1-30`, `mac/Sources/QAutra/Engine/EngineController.swift:44-83,122-135`). 일반 QA 설치 제품은 이 개발 환경 전제를 그대로 사용자에게 넘길 수 없다. 설치·의존성 준비·helper 표시·권한·업데이트·자료 보존은 디자인과 별도의 구현/배포 작업 범위다.

## 15. 구현 순서와 제품 출시 증거

순서는 우선순위이지 나머지 범위를 없애는 합의가 아니다. 전체 지원 대상에 대한 미검증은 계속 표시한다.

1. **실행 계약과 데이터 모델:** 확정 revision·필수 범위·사전조건·권한·소유권·전체 판정·idempotency를 먼저 연결한다. 실패 영상과 정리 조건도 첫 실행 전부터 포함한다.
2. **종단 흐름:** 서로 다른 형식의 시나리오를 앱/외부 입력으로 받아 검토→실제 Chrome과 이질적인 Safari/모바일 경로→결함 검출→실패 영상→리포트를 연결한다. 첫 Chrome 성공으로 나머지를 완료 처리하지 않는다.
3. **일반 QA UX:** code/CLI 없이 확정 시나리오 실행, 환경 점검·중지·실패 분석·새 attempt 비교. 원래 대화가 없는 다른 QA 담당자로 검증한다.
4. **고장·오염·장시간 검증:** worker/app crash·sleep·연결 단절·disk full·녹화 중단·부분 setup/cleanup·업데이트/migration·대용량 입력을 다룬다.
5. **검증된 동시 실행:** 기본 순차 결과를 기준으로 독립 자원만 병렬화하고 간섭·오염·증거 귀속·취소/복구를 확인한다. 모델 없이 동일 정책으로 결정되는지 검증한다.

### 출시/지원 선언의 인수 기준

- 서로 다른 문서 형식에서 원 TC의 단계·기대값·전제 누락을 검출한다. 일부 assertion 누락/필수 target 누락/0개 실행은 전체 PASS를 막는다.
- 같은 확정본의 반복 실행에서 조건·결과 차이를 기록한다. 특정 횟수 통과를 “항상 재현”으로 홍보하지 않는다. 지원 대상별 반복 횟수·표본·환경·고장 주입 조건을 검증 계획에 먼저 정하고 결과와 함께 공개한다.
- 정상→독립적으로 정의한 제품 결함→복구에서 해당 업무 assertion이 PASS→FAIL→PASS로 바뀐다. setup timeout을 결함 탐지로 세지 않는다.
- no-refresh chain, 세션 단절, 다른 계정의 동일 재고, tenant reset 충돌, 공유 backend의 별도 클라이언트를 검증한다.
- 실행 전/dispatch 직후/응답 유실/녹화 중/최종화 중 취소·crash에서 중복 변경·타인 자원 정리·오염 자원 재사용이 없다.
- 실패 영상의 올바른 target/attempt·첫 관련 동작·실패 구간·재생 가능성을 확인한다. 누락·만료를 정상 영상으로 표시하지 않는다.
- host 포커스·포인터·클립보드가 전체 수명주기와 OS dialog/IME 경로에서 간섭받지 않는지 실제 측정한다.
- 사용자가 제출한 문서/페이지/로그의 지시가 파일 접근·외부 전송·위험 동작·기대값·실행 순서를 확장하지 못한다.
- 다른 QA 담당자가 설치→프로젝트 준비→문서 가져오기→확정본 실행→결과/영상 확인→새 실행까지 수행한다. 새로운 필수 모델 키·수동 DSL을 요구하지 않는다.
- 정상/차단/오류 상태를 keyboard·화면 읽기·좁은 창에서 사용할 수 있다. UI의 처리량·연결·녹화·보존 설정이 실제 backend 상태와 일치한다.

아래 반례를 인수 계획에 포함한다. 실제 실행한 결과가 아니라 출시 전에 확보할 증거다.

지연·FPS·최대 동시 개수·오탐률 등 측정되지 않은 수치는 여기서 만들어 넣지 않는다. 지원 가능한 조합과 실측 상한을 확인하기 전에는 해당 성능/지원 보장을 출시 문구에 쓰지 않는다.

## 17. 독립 적대적 리뷰와 반영 기록

두 독립 `adversarial-sol61` 검토가 이 문서의 초안을 읽었다. `ProductTrustAdversary`는 제품 신뢰·발행·권한·복구, `SpaceDesignAdversary`는 자원·입력 경계·UI 전달 계약을 검토했다. 동일 모델 계열의 독립 검토이며 교차 모델 검증이나 Agent Flow의 공식 코드 multi-review 통과가 아니다.

두 검토 모두 구조 선택을 뒤집을 근거는 없지만 당시 초안을 최종 전달 기준으로 보기에는 공백이 있다고 판단했다. 지적 15건(P1 8건, P2 7건)을 다음과 같이 반영했다. 우선순위는 설계 수정 순서이며 재현된 제품 결함/보안 취약점의 확정 등급이 아니다.
