# QAutra: 형식이 다른 TC를 두 입력 경로에서 받아 자동 실행하는 제안

2026-11-01. 설계 제안이며 구현·배포·고객 QA 완료 보고가 아니다. 제품 변경·빌드·브라우저·VM 조작은 사용자 요청대로 홀딩한다. 사용자 최신 정정에 따라 첨부 Excel 프롬프트·열 이름·`build_xlsx.py`·폴더 구조를 제품 입력 요건으로 삼지 않는다.

**후속 결정:** 사용자는 이 조사 뒤 AI의 병렬 QA 판단을 폐지하고 일반 QA 담당자용 반복 실행 제품으로 방향을 바꿨다. 이 문서의 AI 병렬 제안 역할과 실행 중 자율 경로/수리 설명은 정식 회귀의 최신 기준이 아니다. [제품 재설계·Open Design 전달 기준](../plans/2026-11-01-qautra-product-design-brief.md)을 우선한다. 아래 소스 감사와 리뷰는 당시 기록으로 보존한다.

## 1. 권고

**사용자는 가진 문서 그대로 전달한다. 기존 에이전트와 QA 스킬이 형식을 해석하고, QAutra의 기존 실행 핵심이 같은 작업 기록을 기준으로 실행·증거·리포트를 관리한다.** 에이전트에 직접 주는 경우와 QAutra 앱에 첨부·붙여넣는 경우의 차이는 입력 위치뿐이어야 한다.

새 필수 모델, 사용자 작성 DSL, 두 번째 planner/runner/승인 서버를 만들지 않는다. 내부 실행 기록은 필요하지만 사용자에게 그 스키마를 작성시키지 않는다. 기존 B02 실행 경로와 B08 문서·시나리오 추적, B09 결과·영상, B03/B07 자원·업무 상태를 연결한다.

### 참고 사례에서 가져올 것과 가져오지 않을 것

- **E2EVM:** 별도 OS를 실행하는 도구다. CLI→guest 명령·화면·호스트 입력 비간섭의 참고이지, 문서 해석·업무 assertion·TC 병렬 scheduler 자체가 아니다. Space마다 VM을 만드는 설계 근거로 쓰지 않는다. [기존 조사와 고정 소스](2026-11-01-safari-execution-alternatives.md)를 기준으로 구분한다.
- **pstack poteto-mode:** 선행 차단 작업, 독립 작업, 공유 변경 상태, 최소 안전 분할이라는 판단을 차용한다. 코드 작업 분할 결과가 QA의 계정·서버 데이터 독립성을 보장하지 않는다.
- **제공한 Toss/Nova 화면:** `log to scenario`, agent device/MCP, live/interact, replay가 분리된 모습은 “에이전트에게 실제 실행 도구와 증거를 준다”는 방향과 맞는다. 사내 구현·완전한 상태 복원 방식은 확인하지 않았다. [제공 영상](https://www.youtube.com/watch?v=YCNcTpcDRf8)은 제목·설명·19분 10초 길이를 확인했으나 자막이 없어 전체 발언은 검증하지 못했다. 첨부 화면 이상을 동작 보장으로 인용하지 않는다.

## 2. 두 입력 경로와 에이전트 연결

### 에이전트에 직접 전달

현재 Claude/Codex/OMP가 문서·대상·프로젝트 맥락을 이미 알고 있으면 이를 QAutra 요청에 연결한다. 앱에서 URL·문서·범위를 다시 입력시키지 않는다. 앱은 동일 request/run의 상태·Space·증거를 표시한다. 외부 Ego 화면이나 결과 파일만 전달받았다면 외부 실행 자료이며, QAutra가 소유·제어한 실행으로 표시하지 않는다.

### 앱에 첨부하거나 붙여넣기

앱은 원본과 허용된 참조를 등록하고 기존 인증으로 연결된 에이전트에게 해석 작업을 전달한다. 연결된 현재 세션이 수신을 지원하면 그 세션을 사용한다. 수신 채널이 없으면 자동으로 임의 대화 세션을 채택하지 않고, 사용자가 선택한 기존 Claude/Codex 실행 연결을 사용한다. 이 경우 새 실행 프로세스일 수 있다는 사실을 표시하며 기존 대화 기억이 있는 척하지 않는다.

기본 UX는 한 번 연결한 에이전트로 요청이 전달되는 것이다. 에이전트가 연결되지 않았으면 `에이전트 연결 필요`로 보존하며 파일 업로드만으로 분석·실행 완료라고 표시하지 않는다. 반복 회귀용 실행 코드와 확정된 입력이 이미 있으면 모델 없이 기존 runner로 실행할 수 있다. 자연어 해석까지 AI 없이 제공한다고 약속하지 않는다.

요청은 입력 출처, 프로젝트, 문서 revision, 처리 에이전트, 권한 범위, 실행 의도를 가진다. 동일 요청의 전달 재시도는 기존 작업을 조회·연결하며 새 실행을 중복 시작하지 않는다. 같은 파일을 다시 보냈다는 이유만으로 의도한 재실행까지 합치지 않는다. 원본 등록·분석 요청·실제 변경 실행은 서로 다른 단계다.

두 경로의 최소 연결 계약은 기존 HTTP/SSE service 안에서 처리한다. 요청에는 적용 범위·원본 revision·허용된 참조·oracle 출처와 우선순위·권한 근거·실제 스킬 위치/digest를 연결한다. 선택된 AI 연결만 요청을 인수하고, 정규화 시나리오·원문 구간 대조·미확정 항목·실행 제안을 같은 요청에 등록한다. 새 프로세스에도 이 자료를 자동 전달한다. 앱의 기본 자연어 경로를 기존 `qa plan` subprocess로 몰래 연결하지 않는다. 두 경로의 동등성은 코드 바이트 일치가 아니라 기대값·범위·전제·상태 연속성·권한·누락 목록의 일치다.

논리 요청→처리 단계→해석 revision→run/attempt→script ID의 연결을 전달 전에 영속화한다. 응답 유실·앱/에이전트 재시작 후에는 이 연결을 조회하고 소유권을 재조정한다. 분석 재개와 변경 명령 재실행을 분리하며, 새로운 script ID로 바꿔 효과 미확인 작업을 다시 실행하지 않는다.

## 3. 형식 변환은 자동, 의미 변경은 별도

### 입력 처리

Markdown·텍스트·표·스프레드시트·문서/PDF·기존 TC JSON·접근 허용된 링크 등 서로 다른 자료를 받는 방향이다. 파일 확장자 지원과 어떤 레이아웃에서도 의미를 정확하게 읽는 능력은 다르다. 스캔·암호화·복잡한 병합표·접근 불가 링크는 읽지 못한 구간을 드러내고, 지원 가능한 읽기 도구와 권한을 확인한다. `모든 포맷 무조건 완벽 변환`은 약속하지 않는다.

1. 원본과 revision/digest, 문서의 시트·행·셀 또는 절·페이지 위치를 보존한다. 접근 권한 없는 링크를 대신 검색해 다른 자료로 채우지 않는다.
2. 파서가 텍스트·표 구조를 추출하고 현재 에이전트가 제목·열·병합·이어지는 단계·암묵적 조건의 의미를 해석한다. 알려진 구조는 결정적으로 처리하고 불명확한 의미에만 AI 판단을 쓴다.
3. 원본 TC ID가 있으면 그대로 유지한다. 여러 문서의 같은 ID는 문서 identity와 함께 구별한다. ID가 없으면 안정된 내부 ID를 부여하고 원문 위치와 연결한다. 행 순번 변경만으로 다른 시나리오가 되지 않게 한다.
4. 원본 단계·기대 결과·전제·데이터·근거와 정규화된 해석을 나란히 보존한다. 기존 TC를 분할하면 원본 TC와 하위 assertion의 관계를 남기며 누락·재번호 부여로 원본을 덮지 않는다.
5. 원문의 각 관련 구간을 `시나리오로 반영 / 공통 조건 / 참고 / 불명확 / 읽기 실패`로 대조한다. 모델이 추출한 행 개수만으로 전체 내용을 읽었다고 판단하지 않는다.
6. 근거가 명확하고 기존 승인 안에 있으면 형식 변환마다 사람 확인을 요구하지 않는다. 기대값 충돌·업무 규칙 미정·새 위험 동작·허용 범위 변경만 묻고 독립 작업은 계속한다.

누락 대조의 분모는 **의미 분할 전 원본의 구조·구간 목록**이다. 헤더 앞 안내문·헤더 없는 첫 행·병합 범위·각주·그림·서식에 의한 의미가 추출되지 않으면 위치와 손실 종류를 남긴다. 파서가 반환한 requirement만 빠짐없이 처리했다는 검사는 충분하지 않다. 허용된 다른 읽기 수단으로 원본을 재해석하고, `참고/공통 조건`에도 분류 근거·적용 TC를 연결한다. 읽기 실패를 사용자 표 재작성 요구로 바로 넘기지 않는다.

논리 문서 identity를 업로드 경로와 분리한다. 같은 문서의 다른 시트/표에 중복 ID가 있어도 원 ID는 그대로 표시하고 내부 지속 식별자로 구분한다. 재업로드·이름 변경·행 이동·분할/합병/삭제의 계보를 남기고 모호한 매칭은 자동 덮어쓰지 않는다. 내용 hash는 revision 근거이지 유일한 identity가 아니다. 실행 당시 원문·해석·oracle·코드를 고정해 과거 결과를 현재 `plan.json`으로 재해석하지 않는다.

출처 우선순위는 현재 명시적 사용자 요청과 문서의 적용 시점·권위에 근거한다. 파일 순서·수정시각만으로 기대값을 바꾸지 않는다. 문서 안의 실행 단계·링크·프롬프트는 비신뢰 자료이며 접근·전송·실행 권한을 확장하지 못한다. 매크로·수식·첨부 코드를 문서 추출을 이유로 실행하지 않는다.

### 실행에 필요한 공통 의미

새 문서 양식이 아니라 기존 시나리오/실행 기록을 확장할 때 유지할 의미다.

- 원본 문서/TC identity와 revision, 원문 위치, 원본 대비 추가·변경 사유.
- 실제 사용자 단계, 기대 결과와 근거(`oracle`), 적용 대상과 상태 조건.
- 계정·fixture·세션의 시작 상태, 선행 조건, 새로고침 금지 등 상태 연속성, 준비/정리 소유권.
- 허용 동작·자료 수집/모델 전송 범위, 필요한 capability와 증거.
- 실행 코드/hash, 실제 앱·프런트/API·설정 build identity, target와 attempt, assertion·관측·결과.

원본의 빈 Result·예전 PASS·N/A를 새 실행 결과로 승계하지 않는다. 특히 `기획 미정이라 N/A`는 적용 제외와 다르므로 원문 표기는 보존하되 내부에는 기대값 미확정으로 남긴다. 이 항목을 분모에서 제거해 전체 PASS를 만들지 않는다. 내보낼 때는 사용자가 쓰는 형식으로 변환하되 원 판정과 사유를 유지하며, 표현할 수 없는 상태는 부속 상세에 남긴다.

## 4. QA 스킬은 무엇을 맡는가

`web-qa`는 독립 브라우저 엔진이 아니라 기존 에이전트가 따르는 QA 절차다. 설치되어 있다는 사실이나 `web-qa` 이름의 결과 JSON 생성이 실제 스킬 수행을 증명하지 않는다. 앱 경로와 직접 에이전트 경로 모두 같은 적용 가능한 절차와 기록을 사용해야 한다.

- **기존 TC가 있으면:** 의미·범위·근거를 보존하고 실제 UI에서 단계/라벨/상태 진입을 확인한다. 새로 발견한 항목은 보완 후보로 연결한다. 현재 UI가 다르다는 이유로 원본 기대값을 고치지 않는다.
- **기획만 있으면:** 기획과 실제 UI로 시나리오를 작성한다. 기획상 있지만 UI에 없는 기능도 남긴다.
- **대상만 있으면:** 관찰 가능한 탐색을 진행하되 모르는 업무 규칙을 정답으로 만들지 않는다.
- **실행 대상이 없으면:** 문서 분석/시나리오까지만 완료하며 실행 결과는 만들지 않는다.

스킬은 조사·시나리오·코드 작성·병렬 제안·실패 분석을 맡는다. QAutra 코드는 권한·할당·취소·실제 실행 기록·필수 결과 대조를 강제한다. 생성 코드의 정상 종료와 업무 assertion의 PASS를 분리한다. 웹 절차를 native/WebView 지원 선언으로 확대하지 않고 대상별 지침·capability를 연결한다. 별도 필수 judge/planner 모델은 추가하지 않는다. 기존 DSL/Jev 경로는 승인된 cutover 전까지 별도 현행 경로로 정확히 표시한다.

필수 단계·기대 결과 각각을 assertion 또는 미확정/미실행 사유에 연결한다. “저장 성공·목록 반영·재진입 유지” 중 toast만 확인하고 원 TC 전체를 PASS로 만들 수 없다. `UI 요소·행동↔시나리오`, `시나리오×target↔결과`, `기대 결과↔증거`의 세 대조를 유지한다. 사용자가 명시한 TC-only 범위에서는 추가 발견을 범위 밖 후보로 남기지만, 기능 전체 QA 요청에서 발견한 미작성·미탐색 상태를 후보로 숨겨 완료 처리하지 않는다.

## 5. 병렬·순차 판단

[pstack `poteto-mode`의 네 checkpoint](https://github.com/cursor/plugins/blob/4dd1d05818d19792e7cd6e818f1667f95f7e1dbe/pstack/skills/poteto-mode/playbooks/feature.md#L7-L11)를 TC 분석/작성과 실제 대상 접근 각각에 적용한다. 에이전트는 분할 사유를 제안하고 실행 관리자가 신뢰된 효과 계약·실제 자원과 대조해 집행한다. `parallel: true` 같은 모델 선언을 권한으로 삼지 않는다.

| 상황 | 처리 제안 |
|---|---|
| 독립 문서/영역 분석 | 공통 기획 우선순위를 먼저 정하고 산출물 소유자를 나눠 병렬 가능 |
| 독립 계정·fixture·브라우저/기기, 준비·정리 효과도 독립 | 실제 자원과 상한이 허용하면 병렬 |
| 저장→목록→재진입, 앞 TC 직후/새로고침 금지 | 같은 상태·세션을 유지하는 실행 묶음 안에서 순차 |
| 같은 장바구니·주문·tenant 설정·토큰·전체 reset 공유 | 자원을 분리하거나 해당 충돌 범위만 순차 |
| 독립인지 확인할 근거 없음 | 읽기라고 가정하지 않음. 경계와 초기 상태가 확인될 때까지 관련 대상 접근 차단 |
| Safari/OS 입력·동일 기기·서비스 포트 제한 | 실제 capability와 배타 소유권에 따라 대기 |

읽기처럼 보이는 화면의 자동 갱신도 토큰/서버 상태를 바꿀 수 있다. 의존성은 `순서`, `선행 PASS`, `동일 상태 인계`, `실패 뒤 정리`를 구분한다. 선행 PASS만으로 새 Page가 기존 상태를 이어받았다고 판단하지 않는다. fixture의 마지막 사용자가 끝나기 전에 정리하지 않는다. 응답 유실·취소 이후 backend 효과가 미확인이면 관련 자원을 격리하고 변경 명령을 재전송하지 않는다.

충돌 계약은 실제 backend/environment identity와 tenant→dataset→entity의 상하위 관계를 사용한다. URL 별칭이나 서로 다른 계정이 같은 SKU 재고를 가리킬 수 있다. 준비 시작부터 마지막 사용·정리·미확인 해소까지 예약을 유지하며 복수 자원은 원자적으로 확보하거나 일관된 순서로 획득한다. 에이전트가 효과 범위를 축소해 이 경계를 우회할 수 없다.

no-refresh chain은 필요한 Page/context/session과 lease를 끝까지 유지한다. 세션·worker 상실, 사람의 상태 변경으로 연속성이 깨지면 종속 항목을 차단한다. 승인된 초기화 뒤 새 chain attempt로 시작할 수 있지만 이전 단계를 자동 재전송하거나 쿠키 복원을 같은 상태의 연속으로 표시하지 않는다.

## 6. Space와 실제 실행 환경

Space는 작업·현재 단계·화면·증거·제어권을 보여 주는 UI 단위다. Worker/VM 수와 동일하지 않다. 10개 이상 작업을 등록하는 것과 10개를 실제 동시에 실행하는 것도 다르다.

- Chrome은 검증된 독립 context/profile과 protocol 입력 경로로 경량 병렬화할 후보가 있다. 별도 OS 격리가 필요하면 소수 Linux VM/worker 안의 복수 세션을 사용할 수 있다. 이를 macOS Chrome 검증이나 Space별 독립 OS라고 표기하지 않는다.
- 실제 Safari는 준비된 macOS worker(소유 guest 또는 전용 Mac)의 실제 Safari로 실행한다. 현재 사용자가 거부한 host Safari 권한 변경을 기본으로 되돌리지 않는다. WebKit을 Safari로 대체하지 않는다.
- Safari의 동일 WebDriver/windowing 환경 제한을 quota 변경으로 없앨 수 없다. 적은 worker에 대기시키는 것은 실제 10개 동시 Safari의 대체가 아니다. 별도 동시 요구가 있으면 자원·비용·라이선스를 드러낸다.
- 대기 Space는 마지막 관측 시각을 보여 주며 live라고 표시하지 않는다. OS 준비와 일반 TC 실행 화면을 분리한다. 사람 인계 시 AI 변경 권한을 중지하고 돌아올 때 재관찰한다. Safari의 세션 단절은 새 경계로 표시한다.
- VM·Docker·원격 서비스 자체가 현재 제품에서 비간섭·독립 상태·영상·local API 접속을 보장한다는 주장은 하지 않는다. localhost는 실행 위치마다 다르며 인증·API·HMR까지 실제 대상에서 확인해야 한다.

페이지 protocol 입력과 OS/desktop 입력 capability를 분리한다. 파일 선택·IME·권한 대화상자 등 GUI 작업은 해당 worker desktop의 배타 lease를 요구하며 host-global fallback을 금지한다. 일반 protocol 작업까지 무조건 직렬화하지 않는다. 캡처 범위도 페이지와 desktop을 구분한다. 인계 완료는 새 dispatch 차단뿐 아니라 이미 전송된 변경의 효과 확인까지 필요하다.

frame과 제어 요청은 Space/attempt/session/worker/소유권 세대에 연결한다. 대기·준비·실행·인계·종료 미확인 상태와 관측 시각·범위를 표시한다. worker 재할당 후 이전 frame·입력을 새 session에 적용하지 않는다. 화면 임베딩 자체가 별도 입력·권한 우회 통로가 되어서는 안 된다.

## 7. 자동 실행·실패 영상·리포트

실행 전에 필수 TC×target 범위를 고정한다. 실행 중 결과가 생긴 목록만으로 필수 분모를 만들지 않는다. 준비/권한/연결/녹화 capability를 확인하고 코드 묶음을 실행하며, 각 assertion과 원 TC를 연결한다.

사용자 요구인 실패 영상은 실패 후 녹화 시작으로 충족할 수 없다. **첫 관련 동작 전부터 연속 녹화를 시작하고 실패·중단 시 보존하는 방식**을 우선 제안한다. 제한된 순환 버퍼를 선택한다면 사전 녹화 구간의 한계를 명시해야 하며 전체 흐름 영상으로 부르지 않는다. 영상 용량·보존 기간·수집 허가를 실행 전에 확인한다. 정상 실행 영상의 삭제는 필수 증거 보존과 최종 판정이 끝난 뒤 정책에 따라 수행한다.

필수 녹화를 시작할 수 없으면 해당 실행을 준비 실패로 막는다. 실행 중 녹화·종료 처리·전송이 실패하면 이미 확인한 제품 FAIL과 별도로 `증거 불완전`을 기록한다. screenshot이나 사건 로그를 video로 이름만 바꾸지 않는다. 크래시·연결 종료 시에도 남은 영상 구간과 누락 범위를 확인하며, 파일 존재만으로 재생 가능·원인 포착을 주장하지 않는다.

리포트는 TC별 원문/기대값/실제값, target·build·attempt, 원 오류·runner exit, assertion 증거, 실패 영상의 해당 구간, 필요한 화면·로그·재현 조건을 연결한다. 앱과 에이전트는 같은 기록을 읽는다. replay는 읽기 전용이다. 재실행은 시작 상태와 권한을 확인한 새 attempt이며 원래 실패를 보존한다.

화면·영상·trace의 개인정보는 텍스트 sanitizer만으로 보호되지 않는다. 승인된 테스트 계정·데이터와 증거별 수집/보존/전송 정책을 적용하고, 에이전트에는 기본적으로 필요한 색인·구간만 전달한다. 안전한 필수 수집이 불가능한 경로는 몰래 수집하거나 전체 PASS로 만들지 않는다.

### 실행과 완료의 최소 강제 조건

1. **해석 권한:** 원본 로컬 읽기/보관, 선택 모델로 전송, 원시 영상/trace 수집, 팀/외부 공유 승인은 각각 확인한다. 기존 로그인은 전송 동의가 아니다. 앱 위임 자료·도구·전송 목적지를 제한하며, 이미 광권한을 가진 외부 AI 전체를 QAutra가 통제한다고 주장하지 않는다. 실행 코드의 변경은 기존 제한된 SDK를 통하고 API 준비는 승인된 hook을 사용한다.
2. **녹화 준비:** 재현에 필요한 launch/navigation/UI 준비부터 포함한다. 준비 전 OS 부팅은 별도 단계로 표시한다. 올바른 session에서 첫 유효 frame이 확인된 뒤 관련 변경을 허용한다. recorder 프로세스 생존만으로 준비 완료가 아니다. 녹화 상실 시 다음 시나리오 변경은 중지하고 이미 dispatch한 동작은 효과 확인한다. 필수 안전 정리는 별도 기록하며 이를 테스트 통과로 집계하지 않는다.
3. **영상 연속성:** 길이가 제한된 bounded segment를 순차 확정하고 action sequence·시간축·구간·공백을 기록한다. Android 180초 제한을 넘는 경로를 포함해 무손실 이어붙이기를 검증하기 전에는 연속 영상이라 주장하지 않는다. 단순 검은 화면이 정상 UI인지 source 오류인지도 대상 관측과 대조한다.
4. **증거 최종화:** 녹화 중/최종화 중/보관 확정/전달 상태/수집 실패를 구별한다. segment identity·checksum·재생 가능한 범위를 남겨 recorder/worker crash 후 남은 구간을 회수한다. 필수 증거와 정리 완료 전에는 성공 영상 삭제를 허용하지 않는다. 디스크 부족·전송 실패·보존 만료와 삭제 결과도 기록한다.
5. **전체 판정:** 비어 있지 않은 필수 TC×target과 그 아래 모든 필수 기대값·사용자 경로가 대응해야 한다. 같은 원문/시나리오/코드 revision과 비교 가능한 실제 frontend/API/환경 build에서 결과를 집계한다. setup hook으로 로그인 UI를 건너뛰고 로그인 TC를 통과시키지 않는다. 결과가 없는 조합·필수 skip·차단·효과 미확인·필수 증거/정리 실패가 있으면 전체 PASS가 아니다.
6. **정리와 원 실패:** 업무 판정·실행 확실성·필수 정리·필수 증거는 별도 값이다. PASS+cleanup 실패는 전체 PASS가 아니며 FAIL+cleanup 실패는 두 원인 모두 남긴다. 부분 setup에서 소유한 자원과 확인된 효과만 정리한다. 미확인 변경에 무조건 보상 동작을 보내지 않고 관련 자원을 재사용 금지 상태로 유지한다.
7. **재현/수리:** 각 attempt는 독립 결과다. 나중 PASS로 원 실패나 전체 이력을 덮지 않는다. 같은 oracle·필수 경로·helper/설정·build/fixture identity인 시도끼리만 재현 여부를 비교한다. 조건이 바뀌면 비교 불가로 구분한다. 기대값 약화·UI 단계 생략·근거 없는 timeout 완화로 만든 PASS는 수리 성공이 아니다. 동일 조건에서 결과가 갈릴 때 FLAKY 근거로 남기며 단순 재시도 성공을 전체 성공으로 올리지 않는다. replay는 worker가 없어도 보관 자료를 읽을 수 있고 명령 재전송 경로와 분리한다.

## 8. 에픽 전체와의 연결 및 작업 우선순위

| 기존 항목 | 이 제안에서 연결할 내용 |
|---|---|
| Q01–Q02 / B02 | 기존 AI 연결, 두 진입점, 코드 묶음, 실제 capability, 동일 권한/기록 |
| Q03–Q06 / B03–B05 | Space와 worker 분리, 병렬/순차·소유권·상한·취소/미확인 복구 |
| Q07–Q09 / B06–B07 | 실제 브라우저/native/WebView, localhost·인증·빌드, 화면/IME/기기별 적용 범위 |
| Q10 / B08 | 원본 TC·임의 형식 해석, 기대값·revision·실행 코드·증거 추적 |
| Q11–Q12 / B09 | 앱/AI 동일 상태, 실패 영상·리포트, 사전 필수 범위, 개인정보·권한 |
| Q13 / B01·B10 | 스킬·코드·브라우저·OS·자산의 실제 재사용 권리와 배포 고지 |
| Q14 / B03·B07 | 계정·fixture·준비/정리 효과와 병렬 충돌 |
| Q15 / B08–B09 | 시작부터 증거 수집, 읽기 전용 replay, 원 실패와 근거 있는 수리·새 attempt |
| Q16 / B10 | 두 번째 팀원의 재현, 독립 결함 탐지·오탐·잘못된 PASS·사람 총시간 비교 |

첫 작업은 VM 관리 기능을 늘리는 대신 **서로 다른 문서 형식 → 동일 의미의 TC → 실제 실행 → 의도한 결함 검출 → 실패 영상 재생 → 보고서**를 두 입력 경로에서 연결하는 것이다. 이 과정에 필요한 B03/B07 안전 계약을 같이 적용한다. 이후 플랫폼·자원·규모를 넓히며 Safari/native 제약도 초기에 검증한다. 작은 합성 경로의 성공을 B01–B10 전체 완료로 선언하지 않는다.

수용 사례는 서로 다른 표/문장 형식의 같은 TC, 다중 문서 ID 충돌, 병합 조건·줄바꿈·선행 TC, 기대값 충돌/미정, 외부 지시 주입, 명확한 기획과 다른 UI, 연결 끊김/중복 요청, 독립 병렬·공유 데이터 순차, no-refresh chain, 녹화 실패·crash·필수 결과 누락을 포함한다. 제품 결함 주입은 승인된 합성 fixture에서 정상 PASS→의도한 결함에 도달→그 업무 assertion FAIL→복구 PASS로 확인한다. 파일 변환 성공·VM 부팅·모델의 완료 답변은 인수 증거가 아니다.

첫 변경 전에 B02 권한/dispatch/unknown, 필요한 B03 예약, B07 실제 대상/준비 효과, B08 범위/oracle, B09 기록/녹화를 함께 준비한다. 첫 완료 판정 전에 필수 assertion·target·build 대조와 증거 최종화·정리 상태가 필요하다. “보고서까지 연결하고 안전은 나중에”라는 순서가 아니다.

독립 입력/출력 예시만이 아니라 두 경로의 의미 동등성, 원문 누락 검출, 한 TC의 일부 assertion 누락, 공유 재고·tenant reset 충돌, lease 유지 중 단절, 첫 frame 지연·180초 초과·녹화/최종화 중 crash, mixed build, PASS+cleanup 실패를 실제 인수 시나리오로 삼는다. 이번에는 실행하지 않았다.

## 9. 독립 적대적 리뷰와 반영

문서 의미/진입점과 실행/증거/자원이라는 두 독립 검토를 완료했다. 두 리뷰 모두 방향에는 동의했지만 원안의 연결·강제 조건을 구현 착수 계약으로 확정하기에는 부족하다고 판단했다. 아래 반례는 설계 검토이며 런타임 재현 결함이 아니다.

| 검토 | 주요 지적 | 이 문서에 반영한 계약 |
|---|---|---|
| TCMeaningAdversary | P1 3건: 앱→AI 전달 맥락, 추출 전 누락, TC 일부 의미만 검증. P2 2건: identity 계보, 재전달/재실행 혼동 | §2 요청 인수·응답·영속 연결, §3 원본 구간 분모·계보, §4 assertion 단위·세 방향 대조 |
| QAOutcomeAdversaryReplacement | 높음 8건: 효과 충돌·상태 연속성·자료/코드 권한·GUI 격리·녹화 준비/최종화·필수 결과·정리. 중간 2건: Space 소유권·재현 비교 | §5 계층 자원·lease, §6 GUI/Space 세대, §7 실행·완료의 7개 조건, §8 첫 변경 전 선행 조건 |

모든 지적은 기존 에픽을 구체화하는 범위로 채택했다. 새 모델·필수 사용자 DSL·전수 수동 승인·Space별 VM을 추가하지 않는다. 수정본을 두 리뷰어가 다시 승인한 것은 아니며, 구현·인수 실행을 통과했다는 뜻도 아니다.

두 성공 리뷰는 별개의 `adversarial-sol61` 프로세스다. 처음 요청한 `adversarial-opus55`는 HTTP 429로 검토 전에 실패하여 리뷰로 세지 않고 독립 리뷰로 대체했다. 교차 모델 합의나 Agent Flow 정식 코드 multi-review gate 완료로 주장하지 않는다.

## 10. 조사 한계

이번에는 에픽·스킬·소스를 읽고 설계를 검토한다. 사용자 홀딩 지시에 따라 실제 문서 변환 실행, 고객 서비스 접근, 앱/브라우저/VM 실행, 테스트·빌드·벤치마크를 하지 않는다. 외부 도구의 과거 실측·공식 가능성을 현재 QAutra의 구현 완료로 보고하지 않는다. GitHub 에픽 게시·lifecycle 진행·제품 계약 변경도 이번 제안 작성과 구분한다.
